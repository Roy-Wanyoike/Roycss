# Review Checklist 04 — npm Publish Pipeline

- **Use:** Tick every box before merging any PR that touches `scripts/publish/`, `.changeset/`, `package.roycss.json`, `.github/workflows/release.yml`, or the publish-related scripts in `package.json`.
- **Who:** The release maintainer (currently: Royford Wanyoike) plus one reviewer.
- **Cadence:** Every PR in the publish domain; full re-review before every npm publish.

## 1. Pre-merge (code review)

### 1.1 Code changes

- [ ] The PR adds/modifies files **only** under `scripts/publish/`, `.changeset/`, `.github/workflows/`, `docs/{adr,threat-models,benchmarks,plans,checklists}/`, or `package.roycss.json`.
- [ ] No changes to `package.json` `dependencies` (only `devDependencies` may grow).
- [ ] No changes to `dist/` (it is build output — must be regenerated by `scripts/build-package.ts`).
- [ ] No secrets, tokens, or PII committed.
- [ ] No `console.log` left in `prepare.ts` / `release.ts` / `validate.ts` (use the structured `log()` helper).
- [ ] All scripts use `process.exit(1)` on failure (not `throw`).
- [ ] All scripts use absolute paths via `import.meta.dir` (not `process.cwd()`).

### 1.2 Publish config

- [ ] `package.roycss.json` has `name`, `version`, `description`, `main`, `module` (or `style`), `types`, `exports`, `files`, `keywords`, `author`, `license`, `repository`, `homepage`, `bugs`.
- [ ] `files` array is explicit (no `"*"` or `"./"`).
- [ ] `files` array includes `dist`, `README.md`, `LICENSE`, `CHANGELOG.md` (and nothing else).
- [ ] `version` matches the version about to be published (or `changeset version` will bump it).
- [ ] `repository.url` points to `git+https://github.com/Roy-Wanyoike/roycss.git`.
- [ ] `engines.node` is set (currently `>=18`).

### 1.3 Changeset config

- [ ] `.changeset/config.json` has `changelog: "@changesets/changelog-github"`.
- [ ] `.changeset/config.json` has `access: "public"`.
- [ ] `.changeset/config.json` has `baseBranch: "main"`.
- [ ] `.changeset/config.json` `updateInternalDependencies` is `patch` (or `false` — single-package repo).
- [ ] Any new changeset file (`.changeset/*.md`) has valid frontmatter: `"roycss": <minor|patch|major>`.
- [ ] Any new changeset file has a non-empty body describing the change.

### 1.4 CI workflow

- [ ] `.github/workflows/release.yml` runs only on `push` to `main` (never on PRs).
- [ ] `permissions:` block has `contents: write` and `id-token: write`.
- [ ] Uses `actions/checkout@v4` (not v3 or older).
- [ ] Uses `oven-sh/setup-bun@v1` (or pinned `bun-version`).
- [ ] Runs `bun install --frozen-lockfile` (or equivalent) — lockfile changes fail CI.
- [ ] Runs `bun run lint` before publish.
- [ ] Runs `bun run build` (or `publish:prepare`) before publish.
- [ ] The publish step uses `bun run publish:ci` (not inline `npm publish`).
- [ ] `NPM_TOKEN` is read from `${{ secrets.NPM_TOKEN }}` — never inline.
- [ ] No `if: github.actor == ...` shortcuts that could be spoofed.

## 2. Pre-publish (gate)

Run locally before triggering the real publish:

- [ ] `bun run lint` exits 0.
- [ ] `bun run scripts/build-package.ts` exits 0 and prints "✅ RoyCSS build complete!".
- [ ] `dist/` contains: `roycss.css`, `roycss.min.css`, `effects.json`, `effects.cjs`, `effects.js`, `effects.d.ts` (6 required files; `roycss.min.css.map` is optional but expected).
- [ ] `bun run publish:validate` exits 0 and prints file count ≤ 15.
- [ ] `bun run publish:prepare` exits 0.
- [ ] `bun run publish:release` exits 0 and prints the final `npm publish --provenance --access public` command.
- [ ] Tarball size (from `npm pack --dry-run`) is < 500 KB compressed.
- [ ] Unpacked size is < 2 MB (warns if exceeded — does not block).
- [ ] `changeset version` was run and the resulting `CHANGELOG.md` diff was reviewed by a human.
- [ ] The version in `package.roycss.json` matches what we intend to publish.

## 3. Publish (CI)

- [ ] PR merged to `main`.
- [ ] `release.yml` triggered automatically.
- [ ] All steps green: checkout → bun install → lint → build → publish.
- [ ] GitHub Actions run is on a `ubuntu-latest` GitHub-hosted runner (not self-hosted).
- [ ] `npm publish` step printed `+ roycss@<version>` and a provenance attestation URL.
- [ ] No `NPM_TOKEN` value appears in the workflow log.

## 4. Post-publish (verification)

- [ ] `npm view roycss` shows the new version.
- [ ] `npm view roycss@<version> --json` has `dist.attestations` (provenance present).
- [ ] The npm package page shows a "Provenance" badge.
- [ ] `npm view roycss@<version> maintainers` lists the expected maintainer(s) only.
- [ ] In a fresh temp dir: `npm install roycss && node -e "console.log(require('roycss').length)"` prints `1569`.
- [ ] The docs site's npm package card shows the new version (if the version is shown in the UI).
- [ ] The CDN URL `https://unpkg.com/roycss@<version>/dist/roycss.min.css` returns HTTP 200.
- [ ] Git tag for the new version was pushed (if `changeset tag` ran).
- [ ] Worklog entry appended under `---`.

## 5. Security (every quarter, or after any token-related incident)

- [ ] `NPM_TOKEN` rotated (delete old, create new, update GitHub secret).
- [ ] npm account 2FA still enabled (auth-and-writes).
- [ ] npm account password is unique and not used anywhere else.
- [ ] Backup maintainer still has access.
- [ ] `bun audit` runs clean.
- [ ] No typosquatted packages (`roycsss`, `roy-css`, etc.) have appeared on npm — if they have, file an npm abuse report.
- [ ] Threat model (`docs/threat-models/04-npm-publish-pipeline.md`) reviewed and still accurate.

## 6. Emergency (suspected compromise)

If you suspect the publish token, the npm account, or a published tarball has been compromised:

1. **Immediately:** `npm access` → revoke the `NPM_TOKEN` from the npm account (this invalidates the leaked token).
2. **Within 1 hour:** Deprecate the affected version(s): `npm deprecate roycss@<version> "Suspected compromise — do not use. Upgrade to roycss@<safe-version>."`
3. **Within 24 hours:** Publish a fixed version (or unpublish if within 72h of original publish).
4. **Within 24 hours:** Rotate the GitHub Actions `NPM_TOKEN` secret.
5. **Within 48 hours:** Notify consumers via the docs site banner + a GitHub security advisory.
6. **Within 1 week:** Publish a postmortem in `docs/postmortems/`.
