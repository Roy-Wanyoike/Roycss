## ADR-S1 — Content-Security-Policy: per-request nonces in production, `unsafe-inline` in dev

- **Status:** Accepted
- **Date:** 2026-07-30
- **Supersedes:** None (refines §2.2 of `docs/adr/07-security-supply-chain.md`)
- **Decision owner:** Security Engineering & Supply Chain domain

### Context

The marketing site is a single Next.js 16 app. It serves:

- React 19 SSR HTML
- Next.js HMR inline scripts (dev only)
- Tailwind 4 inline styles (both)
- framer-motion inline styles (both)
- Radix UI inline styles (both)
- Library CSS injected via `dangerouslySetInnerHTML` (both — library CSS,
  never user content)

A strict CSP without `'unsafe-inline'` for `script-src` is achievable in
production via per-request nonces. The same strict CSP in dev would break
HMR (Next.js injects inline scripts without nonces during dev).

### Decision

**Two-mode CSP** generated by `src/middleware.ts`:

**Dev** (when `NODE_ENV !== "production"`):
```
default-src 'self';
script-src 'self' 'unsafe-inline' 'unsafe-eval';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
font-src 'self' data:;
connect-src 'self' ws: wss:;
media-src 'self' blob:;
frame-ancestors 'none';
base-uri 'self';
form-action 'self';
object-src 'none';
upgrade-insecure-requests;
```

**Production** (when `NODE_ENV === "production"`):
```
default-src 'self';
script-src 'self' 'nonce-{per-request-128-bit-random}' 'strict-dynamic';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
font-src 'self' data:;
connect-src 'self';
media-src 'self' blob:;
frame-ancestors 'none';
base-uri 'self';
form-action 'self';
object-src 'none';
upgrade-insecure-requests;
```

The dev policy is set in `next.config.ts` `headers()`. The prod policy
overrides it in `src/middleware.ts` after generating a 16-byte nonce via
`crypto.getRandomValues`.

### Rationale per directive

- `default-src 'self'` — fallback for any directive not explicitly listed;
  everything not explicitly allowed is denied.
- `script-src 'self' 'nonce-...' 'strict-dynamic'` — only same-origin
  scripts and scripts bearing the per-request nonce can execute. `'strict-dynamic'`
  lets nonce-bearing scripts (e.g. Next.js's own bootstrap) load their own
  dependencies without listing every hash. This is the [Next.js recommended
  pattern](https://nextjs.org/docs/app/guides/content-security-policy) and
  passes Google's [CSP Evaluator](https://csp-evaluator.withgoogle.com/) with
  no warnings.
- `style-src 'self' 'unsafe-inline'` — required because Next.js, Tailwind 4,
  framer-motion, and Radix UI all inject inline styles at runtime. Removing
  `'unsafe-inline'` would require noncing every style injection, which
  Next.js does not support. `style-src 'unsafe-inline'` does **not** enable
  script execution; the residual risk is CSS-based exfiltration, which
  `security/css-exfiltration-check.ts` defeats by banning external `url()` in
  shipped CSS.
- `img-src 'self' data: blob:` — same-origin images, inline data URIs, and
  blob URLs (used by some Radix components for image previews). No external
  image hosts.
- `font-src 'self' data:` — `next/font/google` self-hosts fonts at
  `/_next/static/media/`. No external font CDN.
- `connect-src 'self'` (prod) / `'self' ws: wss:` (dev) — fetch/XHR/WebSocket
  only to same origin. Dev allows WebSocket for HMR. No analytics, no
  third-party APIs.
- `media-src 'self' blob:` — same-origin audio/video, blob URLs for
  dynamically generated media.
- `frame-ancestors 'none'` — strictly stronger than `X-Frame-Options: DENY`.
  Defeats clickjacking.
- `base-uri 'self'` — prevents `<base>` injection from redirecting relative URLs.
- `form-action 'self'` — prevents form submissions to attacker origins.
- `object-src 'none'` — blocks Flash/Java/plugins (defense in depth).
- `upgrade-insecure-requests` — forces HTTP→HTTPS upgrade on every subresource.

### Consequences

**Positive:**
- Production defeats XSS, clickjacking, MIME-sniffing, form hijacking.
- Dev remains usable (HMR works).
- Single source of truth (`src/middleware.ts`) for the prod policy.

**Negative:**
- Adds ~1ms per request for nonce generation.
- `'unsafe-inline'` for styles is a known Next.js limitation (see Rationale).
- Two policies to maintain; divergence is a risk.

### Alternatives considered

1. **CSP `report-only` first, enforce later.** Rejected — the site is small,
   one route, no third-party scripts. We can validate locally with
   agent-browser before shipping. Enforce from day one.
2. **Hash-based CSP (no nonces).** Rejected — Next.js injects different
   inline scripts per route; hash list would be huge and brittle.
3. **`unsafe-inline` for scripts in prod.** Rejected — defeats the entire
   point of CSP.

## ADR-S2 — Dependency pinning strategy: major-version caret + lockfile + overrides

- **Status:** Accepted
- **Date:** 2026-07-30
- **Supersedes:** None (refines §2.1 and §2.6 of `docs/adr/07-security-supply-chain.md`)

### Context

The marketing site has 69 direct runtime deps + 12 direct dev deps =
1,088 transitive packages installed. Three pinning strategies were
considered:

1. **Exact pin** (`"next": "16.2.12"`) — max reproducibility, no auto-patch.
2. **Caret + lockfile** (`"next": "^16.2.12"` + `bun.lock`) — current approach.
3. **Tilde + lockfile** (`"next": "~16.2.12"`) — patch-only auto-upgrades.

### Decision

**Caret + lockfile + overrides**, with three rules:

1. **Direct deps:** pinned to major version via caret (`^N.x.x`). The
   lockfile (`bun.lock`) pins the exact installed version. `bun install`
   reproduces the lockfile; `bun update` bumps within the caret range.
2. **Transitive deps:** managed via `overrides` in `package.json`. Every
   override forces a patched version of a vulnerable transitive dep. The
   override list is documented in `docs/adr/07-security-supply-chain.md` §6.
3. **Tier A artifacts (npm package, VS Code ext, Inspector, CLI, MCP server):**
   `dependencies: {}` — zero runtime deps. Dev-only deps (TypeScript, types)
   are caret-pinned to a major.

### Rationale

- **Caret, not exact pin:** exact pins lose automatic patch upgrades for
  security fixes. `bun audit` becomes the only signal that a patch exists;
  we'd need to manually bump every dep on every advisory. Caret lets
  `bun update` pull patch fixes within the major.
- **Lockfile, not just caret:** the lockfile guarantees reproducible installs
  across CI and dev machines. Without it, two `bun install` runs six months
  apart could resolve to different versions.
- **Overrides, not just upgrades:** some advisories are in transitive deps
  that the direct dep hasn't bumped yet (e.g. `minimatch@3` inside
  `@changesets/cli`). Overrides force the patched version without waiting
  for the direct dep to release.
- **Tier A zero-runtime:** the library's core promise is "Zero JavaScript
  runtime". A single runtime dep in the npm package would break that promise
  and expand the supply chain for every consumer.

### Consequences

**Positive:**
- Patch security fixes flow automatically via `bun update`.
- Reproducible installs across machines.
- Tier A artifacts have the smallest possible supply chain.

**Negative:**
- Caret allows minor-version upgrades that could break (rare for
  semver-compliant packages, but possible).
- Overrides can break transitive deps (mitigated by lint + build + browser
  smoke test after every override change).
- `bun.lock` must be committed and conflicts resolved on merge.

### Alternatives considered

1. **Exact pin everywhere.** Rejected — loses auto-patch; `bun audit`
   becomes the only signal.
2. **Tilde everywhere.** Rejected — too restrictive; minor versions often
   contain security fixes (e.g. `next@16.2.x` fixed 31 advisories from
   `16.1.x`).
3. **No overrides.** Rejected — leaves transitive vulns unpatched when the
   direct dep is slow to upgrade.
4. **Renovate / Dependabot auto-PRs.** Not yet enabled. Future work — would
   auto-PR patch bumps with `bun audit` clean signal. Out of scope for this
   audit.

## ADR-S3 — Contact form spam prevention: honeypot + rate-limit, defer CAPTCHA

- **Status:** Accepted
- **Date:** 2026-07-30
- **Supersedes:** None (new)

### Context

The contact form (`src/app/api/contact/route.ts`) is the only user-driven
write path. It currently has:

- ✅ Input validation (4 layers, see `DESIGN.md` §4.1)
- ✅ Prisma parameterized queries (no SQL injection)
- ✅ React JSX output encoding (no XSS)
- ✅ Same-origin POST + `form-action 'self'` in CSP (CSRF mitigation)
- ❌ No rate limiting
- ❌ No honeypot field
- ❌ No CAPTCHA

### Decision

**Three-layer spam prevention, in priority order:**

1. **Honeypot field (cheap, invisible to humans, catches dumb bots).** Add a
   hidden `website` input to `ContactForm`. If the field is non-empty on
   submit, return 200 OK (so the bot thinks it succeeded) but do not write
   to the DB. **Implementation:** R-2 in `IMPLEMENTATION-PLAN.md`. (Note: this
   requires editing `src/components/roycss/contact-form.tsx` and
   `src/app/api/contact/route.ts`, both owned by other agents — deferred
   until coordination.)
2. **IP-based rate limit (cheap, catches volume attackers).** 5 requests per
   minute per IP, sliding window. Implement in `src/middleware.ts` using an
   in-memory `Map<ip, count[]>` (sufficient for a single-server deployment).
   On limit exceeded, return 429. **Implementation:** R-1 in
   `IMPLEMENTATION-PLAN.md`. (Same coordination issue as R-2.)
3. **CAPTCHA (deferred).** Defer until spam volume exceeds 10 messages/day
   after layers 1+2 are deployed. When needed, use **hCaptcha** (privacy-
   friendlier than reCAPTCHA, no Google account required). The CSP would
   need `script-src` additions for the hCaptcha origin.

### Rationale

- **Honeypot before rate-limit:** honeypot catches bots that submit every
  form field. Rate-limit catches volume attackers. CAPTCHA catches neither
  cheaply but adds UX friction.
- **Defer CAPTCHA:** the site has low traffic (marketing site for a CSS
  library). CAPTCHA adds UX friction + a third-party script + a CSP
  exception. Honeypot + rate-limit is sufficient for the current threat
  model.
- **Return 200 OK on honeypot trigger:** returning 4xx tips off the bot
  that the honeypot was detected. 200 OK makes the bot think it succeeded
  and move on.

### Consequences

**Positive:**
- Zero UX friction for humans (honeypot is invisible).
- Zero third-party scripts (no CAPTCHA origin to allowlist).
- Cheap to implement (one hidden input + one Map).

**Negative:**
- Honeypot can be evaded by a bot that knows the field name (rotate field
  names to mitigate).
- In-memory rate-limit resets on server restart (acceptable for low traffic;
  use Redis if we ever need multi-server).
- No defense against a targeted manual attacker (acceptable — they can
  send 5/min which is 7,200/day, bounded by rate-limit).

### Alternatives considered

1. **reCAPTCHA v3.** Rejected — requires Google account, adds third-party
   script, privacy-invasive (tracks users across sites).
2. **Cloudflare Turnstile.** Viable alternative to hCaptcha; reconsider when
   CAPTCHA is needed.
3. **Akismet.** Rejected — server-side spam filter, requires API key, adds
   network dep.
4. **Proof-of-work (e.g. mCaptcha).** Interesting; revisit if CAPTCHA is
   needed and privacy is a hard requirement.

## ADR-S4 — npm provenance via Sigstore for all published artifacts

- **Status:** Accepted
- **Date:** 2026-07-30
- **Supersedes:** None (refines §2.1 of `docs/adr/07-security-supply-chain.md`)

### Context

The `roycss` npm package is the library's primary distribution surface. A
backdoored tarball would compromise every consumer's build. Three signals
matter:

1. **What was published?** — the tarball bytes
2. **Who published it?** — the npm account
3. **How was it built?** — the CI run that produced it

npm's `--provenance` flag (Sigstore-based) links all three: the tarball is
signed with a Sigstore key, the signature includes the GitHub Actions run
ID, the commit SHA, the workflow filename, and the repository. Consumers
verify with `npm audit signatures`.

### Decision

**`npm publish --provenance --access public` is the only allowed publish
command.** Enforced by:

- `package.json` `publish:ci` script: `NPM_TOKEN=$NPM_TOKEN npm publish --provenance --access public`
- `scripts/publish/release.ts` calls `publish:ci` (not `publish` directly)
- The release checklist requires verifying `npm audit signatures` after
  publish

### Rationale

- **`--provenance`** attaches a Sigstore signature linking the tarball to a
  specific GitHub Actions run. Consumers can verify the tarball was built
  from a specific commit in our repo, not from a maintainer's laptop.
- **`--access public`** ensures the package is publicly readable (default
  for unscoped packages; explicit is better).
- **`NPM_TOKEN` in env, not in a file.** The token is a GitHub Actions
  secret; it never touches the filesystem.

### Consequences

**Positive:**
- Consumers can verify tarball provenance with `npm audit signatures`.
- A compromised maintainer npm account cannot publish a tarball that
  wasn't built in our CI.
- Sigstore's transparency log (`rekor`) provides a public audit trail.

**Negative:**
- Publish only works from GitHub Actions (not a maintainer's laptop). This
  is a feature, not a bug, but slows emergency patches.
- `NPM_TOKEN` must be rotated quarterly or on maintainer turnover.

### Alternatives considered

1. **GPG-signed tarballs.** Rejected — GPG keys are per-maintainer, not
   per-CI-run. Provenance is stronger.
2. **No signatures.** Rejected — no way to detect a backdoored tarball.
3. **PGP + Sigstore.** Rejected — Sigstore alone is sufficient; PGP adds
   key management burden without adding security.

## ADR-S5 — Secret management: env vars + GitHub Actions secrets, no vault

- **Status:** Accepted
- **Date:** 2026-07-30
- **Supersedes:** None (new)

### Context

This repo has exactly three secrets:

1. `DATABASE_URL` — filesystem path to SQLite (`file:./prisma/dev.db`)
2. `NPM_TOKEN` — npm publish token (CI only)
3. `GITHUB_TOKEN` — GitHub Actions default token

No database passwords, no API keys, no SMTP credentials, no OAuth client
secrets.

### Decision

**No vault.** Use:

- **`.env` (gitignored)** for local dev — `DATABASE_URL` only.
- **GitHub Actions secrets** for CI — `NPM_TOKEN` only.
- **GitHub Actions default `GITHUB_TOKEN`** for changesets PRs — no
  configuration needed.

### Rationale

- **Three secrets do not justify a vault.** HashiCorp Vault, AWS Secrets
  Manager, Doppler, etc. all add operational overhead (rotation policies,
  IAM, audit logs) that exceeds the value for a 3-secret repo.
- **`.env` is the Next.js convention.** `@next/env` loads it automatically;
  no `dotenv` dep needed.
- **GitHub Actions secrets are encrypted at rest**, scoped to the repo, and
  auditable via the Actions log.
- **`DATABASE_URL` is filesystem-only.** SQLite has no network listener;
  the "secret" is just a path. Even if leaked, an attacker needs filesystem
  access to read the DB.

### Consequences

**Positive:**
- Zero operational overhead for secret management.
- No vault dep, no vault network calls.
- Secrets are scoped to exactly where they're used.

**Negative:**
- `NPM_TOKEN` rotation is manual (quarterly or on compromise).
- `.env` files are per-developer; no central secret store.
- No audit log for secret access (GitHub Actions logs show "secret was
  used" but not "who accessed it").

### Alternatives considered

1. **HashiCorp Vault.** Rejected — overkill for 3 secrets.
2. **Doppler / Infisical.** Viable for a larger team; revisit if the team
   grows past 5 people or if we add more secrets.
3. **AWS Secrets Manager.** Rejected — would require an AWS account; we're
   on GitHub Actions.
4. **`.env.vault` (dotenv-vault).** Rejected — adds a third-party service
   for a problem GitHub Actions secrets already solves.

### When to revisit

If any of the following happen, escalate to a vault:

- Secret count > 10
- Multi-environment deployments (staging, prod, preview) with different
  secrets per env
- Compliance requirement (SOC 2, HIPAA) that mandates secret access audit
  logs
- Team size > 5 people who need secret access
