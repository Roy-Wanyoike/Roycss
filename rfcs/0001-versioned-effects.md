# RFC-0001: Versioned Effects — the catalog as a SemVer-governed public API

- **Status:** accepted (retrospective — documents the design as implemented
  today; see [`docs/RFC-PROCESS.md`](../docs/RFC-PROCESS.md) §7)
- **Admitted:** with the governance documentation set (PF-005)
- **Area(s) affected:** frontend, release
- **Approvals:** retrospective admission — the design below is shipping,
  and every claim is pinned by an existing test or script (see §9)
- **Supersedes:** none
- **Enforcement:** the pinned corpus tests and the release scripts named
  in §9 — this RFC documents enforced invariants, not aspirations

---

## 1. Summary

RoyCSS's effect catalog is not a folder of stylesheets — it is a
**versioned public API**. This RFC documents the design that already exists
in `src/lib/`: a single canonical TypeScript source for all 1,959 effects,
a stable per-effect schema (`CSSEffect`), hard namespace contracts
(`roycss-` classes, `roy-` keyframes, `--roycss-*` tokens), per-release
regeneration of machine-consumable artifacts in `dist/`, and lockstep
version bumping across the published packages. The catalog's size and
shape are enforced by tests, which is what allows the semver policy
([`docs/SEMVER.md`](../docs/SEMVER.md)) to be a lookup table rather than a
judgment call.

## 2. Problem

A CSS effects library with ~2,000 effects and five consumer surfaces
(the site, the Express backend, the CLI, the MCP server, the VS Code
extension) has one expensive failure mode: **silent drift**. If the site's
catalog, the JSON artifact the backend boots from, the class index the
extension completes from, and the npm package's CSS disagree, every
consumer is wrong in a different way, and "which version am I actually
using?" stops having an answer. The design below exists to make drift
mechanically impossible and version boundaries mechanically checkable.

## 3. Proposal — the design as it ships

### 3.1 One canonical source

All effects live as typed TypeScript data in `src/lib/`:

- `src/lib/roycss-effects.ts` — the aggregate: imports the
  `effects-batch-*.ts` modules (batches 1–52) and exports a single
  `effects: CSSEffect[]` array, plus `allEffectCSS` (the concatenated CSS
  used for server-side injection to avoid FOUC).
- `src/lib/roycss-types.ts` — the `CSSEffect` interface and the
  `EffectCategory` union (the 29 categories) with `categoryMeta`.

There is exactly one source. Every other representation of the catalog
(the site pages, the API responses, the dist artifacts, the docs counts)
is generated from or validated against this array. The README's "Key
numbers" table states the rule: stale docs fail CI, not users.

### 3.2 The `CSSEffect` schema

```ts
interface CSSEffect {
  id: string;            // e.g. "pulse-glow" — unique across the corpus
  name: string;
  category: EffectCategory; // one of the 29
  description: string;
  tags: string[];
  cssCode: string;       // the effect's complete, self-contained CSS
  previewType: PreviewType; // box | text | button | loader | card | background
  childCount?: number;   // child <span>s for loaders etc. (optional)
  previewText?: string;  // text for text/button previews (optional)
}
```

Two properties of this schema are load-bearing:

1. **Effects are self-contained.** An effect's `cssCode` does not depend on
   another effect's CSS — each can be copied alone into a project and
   works. This is what makes the catalog copy-paste friendly and what makes
   per-effect pages (one page per effect, all in the sitemap) honest.
2. **Optional fields only, ever.** `childCount` and `previewText` set the
   precedent for schema evolution: new fields are optional so older
   consumers keep parsing — additive-only evolution is the rule
   ([`docs/SEMVER.md`](../docs/SEMVER.md) §3 item 5).

### 3.3 Namespace contracts

| Namespace | Pattern | Example | Consequence |
|---|---|---|---|
| Classes | `roycss-<id>` | `.roycss-pulse-glow` (built by `getClass("pulse-glow")` in `src/lib/roycss-index.ts`) | Renaming/removing one is a **major** |
| Keyframes | `roy-<name>` | `@keyframes roy-float` | Same |
| Tokens | `--roycss-*` | `--roycss-accent` (defaults in `src/lib/design-tokens.ts`, OKLCH) | Name stable for the major; defaults may shift in a minor with a release note |

Imported effect families are namespaced into the same scheme: the Ferrum
batch imports convert their classes to the `roycss-ferrum-*` family and
their keyframes to the `roy-ferrum-*` family, with colors converted to
OKLCH. Prefixing is what lets a 1,959-effect corpus (and future imports)
coexist without collisions — with the browser, with user code, and with
each other.

### 3.4 Artifacts regenerated per release

The `dist/` directory is a build product, never a hand-edited one:

| Artifact | Contents | Generated by |
|---|---|---|
| `roycss.css` (+ `roycss-critical.css`, `roycss-fallbacks.css`) | the full catalog CSS | `scripts/build-package.ts` (the package build) |
| `effects.json` | the full `CSSEffect[]` (1,959 entries) — the backend's `effects` service reads it at boot | `scripts/generate-effects-json.ts` (catalog regeneration) and the package build |
| `class-index.json` | per-class entries (`className`, `category`, `effectId`, `properties`) for editor tooling | `scripts/generate-build-artifacts.ts` |
| `motion-library.json` | the motion subset for the motion module | `scripts/generate-build-artifacts.ts` |

`scripts/generate-effects-json.ts` documents the regeneration rule in its
header: run it after every effect catalog change so the backend and the
frontend never drift. Release regeneration (§3.5) makes the same guarantee
at the artifact level: what ships is what the TypeScript source compiles
to.

### 3.5 Lockstep versioning

`scripts/release/bump-version.ts` is the only sanctioned way to change the
package version. It bumps the version across the lockstep manifests
atomically — the library manifest, the CLI, the MCP server, and the VS Code
extension (the list lives in `scripts/release/release.config.ts`) — and
writes nothing if any manifest is missing or unwritable. Hand-edited
version strings are a release-review fail. The changelog is generated in
Keep-a-Changelog format by the same release machinery, and the backend's
`version` module reports the real package version rather than a hardcoded
string.

### 3.6 Consumers

- **Site**: renders the catalog from `src/lib/` directly; every effect also
  has a statically prerendered page at `/effects/<id>` with JSON-LD, OG
  tags, and sitemap entries — unknown IDs return hard 404s.
- **backend-node**: the `effects` module serves the catalog from
  `dist/effects.json` (loaded at boot), so the API and the site cannot
  disagree about the catalog.
- **CLI / MCP server / VS Code extension**: consume the artifacts and the
  programmatic exports of `src/lib/roycss-index.ts` (framework-agnostic
  `getClass`, `getCSS`, `getByCategory`, `search`), which is why the
  version lockstep matters — all five surfaces claim the same version
  number, or none of them is trustworthy.

## 4. Alternatives considered

1. **Hand-maintained CSS + JSON.** The state this design replaces: possible
   for hundreds of effects, catastrophic at 1,959 — every count becomes a
   claim somebody has to audit by hand, and drift is found by users.
   Rejected for exactly the drift reason in §2.
2. **A database as the catalog source.** Would make the backend happy and
   everything else (npm package, VS Code extension, static site) unhappy:
   the CSS artifact would still need generating, the site still needs the
   data at build time, and the "clone and run with no database" property
   (the README's quick start promises it) would be lost. Rejected — the
   TypeScript source is the only representation every consumer can share.
3. **Per-effect versioning.** Version each effect individually instead of
   the catalog. Rejected: no consumer can act on 1,959 independent version
   strings; the practical upgrade unit for CSS is the stylesheet, so the
   version unit is the package. Effect-level change management is handled
   by the stability ladder and deprecation register
   ([`docs/DEPRECATION.md`](../docs/DEPRECATION.md)) instead.
4. **No namespace prefixing** (ship bare class names). Rejected
   immediately: collision risk with user code and other libraries is
   certain at this scale; the `roycss-` prefix *is* the namespace contract
   (§3.3).

## 5. Impact on the versioned surface

This RFC invents no new surface — it describes the existing one, which is
why it is admitted retrospectively. Going forward, the mapping of changes
to version bumps is exactly [`docs/SEMVER.md`](../docs/SEMVER.md) §2–4,
with the layers of §3.3–3.6 as the checklist. Two consequences deserve
emphasis:

- The **catalog size is an invariant, not a vanity metric**: 1,959 effects
  and 29 categories are pinned by test, so a change to either is a
  deliberate, reviewable event that updates the pin and the README
  together.
- The **artifact schemas are public API**: `effects.json`'s field set is
  parsed by the backend at boot and by external tooling; changing it
  non-additively is a major and requires this RFC to be amended through a
  successor RFC.

## 6. Risks and known tradeoffs

1. **Known defect, locked.** Batches 30 and 34 ship `ferrum-*` variants
   that re-declare `roy-*` keyframe symbols of the originals (bodies
   identical, second declaration wins — benign at runtime, but payload
   bloat and linter noise). Plus three small non-ferrum keyframe
   collisions. The corpus test locks this as a known-defect baseline so it
   cannot silently widen; retiring it is future work, and the fix must
   respect the namespace contract rather than weaken the test.
2. **Batch-file growth.** 52 batch modules keep individual files reviewable
   but make the aggregate import list long. Acceptable while batches stay
   flat data; a catalog-level reorganization (e.g. per-category modules)
   would be an RFC of its own — internal layout, but it moves the pinned
   imports the tests rely on.
3. **Single maintainer.** The regeneration discipline (§3.4) and the
   lockstep rule (§3.5) are script-enforced precisely so they do not depend
   on one person's memory — the bus-factor mitigation described in
   [`MAINTAINERS.md`](../MAINTAINERS.md) §4.3.

## 7. Migration

None required — the design is shipped. Consumers relying on bare class
names or hand-copied JSON never existed as a supported mode.

## 8. Future work (explicitly not part of this RFC)

- **Per-effect stability labels** (`stable` / `experimental` / `deprecated`
  as schema fields, driving the deprecation register of
  [`docs/DEPRECATION.md`](../docs/DEPRECATION.md)) — proposed direction for
  a successor RFC.
- **Keyframe collision cleanup** (risk item 1).
- **Per-category artifact modules** for smaller-than-full-catalog installs.

## 9. Enforcement (all existing, all in-repo)

| Invariant | Enforced by |
|---|---|
| Exactly 1,959 effects | [`tests/unit/effects.test.ts`](../tests/unit/effects.test.ts) |
| Exactly 29 categories | [`tests/unit/categories.test.ts`](../tests/unit/categories.test.ts) |
| Unique ids; id ↔ `.roycss-<id>` selector correspondence; keyframe uniqueness with the known-defect lock | [`tests/unit/effects.test.ts`](../tests/unit/effects.test.ts) |
| Artifact regeneration from source | `scripts/generate-effects-json.ts` (+ the package build; release scripts regenerate `dist/`) |
| Lockstep version bumping, atomic | `scripts/release/bump-version.ts` + `scripts/release/release.config.ts` |
| Typecheck of the whole surface | `bunx tsc --noEmit` (0 errors) in CI |
| Unit suite over the catalog and index | `bunx vitest run tests/unit` (248 tests) |

This RFC is accepted because §9 is already true. If any row of §9 stops
being true, that is not a documentation update — it is a regression with
an owner (per [`MAINTAINERS.md`](../MAINTAINERS.md) §2).
